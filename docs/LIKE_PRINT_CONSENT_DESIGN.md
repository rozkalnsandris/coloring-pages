# Ausmalwiese — Like/Print consent (#182)

**Current source contract (2026-10-12):** Draft PR #183 implements **Worker-issued v3 credentials**, D1 purpose registration, server-side expiry checks, guarded Like/Print writes and atomic v3 revocation. The old **v2 identifier is accepted ONLY for a one-shot, user-directed Like erasure** when the browser had previously allowed Like and still holds a valid secure v2 token. Normal personalized requests reject v2; on successful withdrawal the client removes the local v2 ID and sends it only in `POST /api/stats/erase-likes`. There is no automatic retry and a failed/unknown response must not be labelled successful. The v2 delete route has no broad retroactive erasure guarantee for backups/logs. PR #158 (`b854d6aa124a935215b02d226c0da50302fa1228`) describes v3 in its legal-page Draft; neither PR has a legal sign-off. `cloudflare/stats-v3-migration.sql` remains unapplied; the real `CONSENT_TTL_SECONDS` and retention/DSAR rules remain unapproved. **NO MERGE / NO LIVE.**

**Expired/missing v3 consent handling (2026-10-12 source-only):** On an explicit Worker `credential_expired` rejection of a purpose-authorized personalized Like/Print call, the frontend discards only the matching old browser token and choice and presents unchecked Like/Print options for a new affirmative decision; `GET /page` remains anonymously usable. No implicit renewal occurs from a retained local consent flag or merely clicking Print. Print telemetry uses `fetch(..., keepalive:true)` rather than `sendBeacon` so the response can be inspected while the print flow proceeds independently. Missing tokens fail closed rather than automatically minting a credential. A legacy v2 identifier is preserved for explicit deletion rather than silently discarded; unrelated 403, transport error and stale-tab response must not cause false expiry or erase a newer token. No chosen 90-day TTL, scheduled D1 cleanup, legal decision or deployment is implied; see paired PR #158's design proposal at `2ace3bfdccb52a52d00a8074dd18c1c8535dea00`. This does **not** remove old D1 Likes, D1 recovery data or prove a parent's consent.

**Legacy same-choice recovery (2026-10-12 Draft source):** A previously Like/Print-consented browser carrying a high-entropy `v2-` token or an unrecognized weak legacy ID can open settings and deliberately reconfirm the *same* purpose choices to request a new Worker-issued v3 credential; a same-value choice no longer short-circuits issuance. A valid v2 token with previous Like permission and continuing Like opt-in requires a **separate explicit confirmation of deleting old active Likes** before replacement: exactly one deletion-only `POST /erase-likes` is attempted, and a failed/ambiguous response never triggers an automatic retry or a new v3 issuance. Previously stored v2 Likes are not migrated or silently discarded. If a v2 Like is explicitly withdrawn, the already-established withdrawal-only erasure path remains. An unrecognized weak legacy ID cannot prove historical Like ownership: the interface expressly warns before continuing that previous Likes cannot be confirmed deleted, does not submit the weak ID to the Worker, and points to the manual rights contact. Blocked localStorage never grants new tracking. A rejected confirmation leaves the old credential and choice unchanged. An ID changed in another tab while v2 deletion was pending halts that upgrade. A new consent event is an opt-in event, not proof of parental authorization; 90-day retention, cleanup, legacy orphan records, Cloudflare logs, and GDPR Art. 8 remain unapproved. **NO MERGE / NO LIVE.**

**Exact-proof v2 erasure guard (2026-10-12 Draft source):** The page-session-only deletion attempt stores the exact old v2 proof with state `attempted` or `confirmed` **in memory**, never in new localStorage, D1, or a retry queue. Success for proof A never confirms deletion of different proof B. A failed/network-ambiguous B stays blocked from repeat submission for B during the same page session; switching to another eligible proof requires its own explicit confirmation and one independent deletion request. Cross-tab proof swaps after a response remain guarded. Automated tests cover A→B success, A success/B failure or ambiguous network outcome, and A failure/B success. After page reload this in-memory record is gone, so it is not a durable server-side anti-retry guarantee, nor proof of deletion from D1 backups/logs. Owner/legal retention, DSAR and GDPR Art. 8 gates stay open. **NO MERGE / NO LIVE.**

## Historical minimal v2 design (superseded by v3 source)

- Keep the small German fixed banner: **Alle ablehnen**, **Einstellungen**, **Alle akzeptieren**. Settings have independent initially-unchecked Like and Print choices. Reopening and withdrawing consent must be easy. No site-wide blocking of browsing or printing.
- Save only `coloring-pages-consent-v1` containing purpose booleans, version and time in localStorage. Use the existing securely generated `v2-` random visitor ID only for opted-in purposes; old pre-consent IDs are never silently read or reused. The Like and Print check remains purpose-specific, including across tab changes. **Consent time in localStorage is not verified individual consent evidence**; GDPR Art. 7(1) and TDDDG §25 still require review.
- Keep reversible Likes, anonymous aggregate Like counts, all existing Print metrics, and the cloud-hosted Worker/D1 setup. New Print intents count **only with Print consent**; browsing, PNG download and A4 printing remain available without any opt-in. Historical counters are not reset or relabelled as physically printed pages.
- Personalized page status uses HTTPS **POST** body on new clients. Anonymous GET stays in place. Transitional legacy personalized GET may expose old visitor IDs in URLs and remains a documented separate security sunset decision.
- Like withdrawal with a currently available valid `v2-` identifier **immediately stores the new consent choice, retires the local ID, then attempts exactly one** origin-checked rate-limited `POST /api/stats/erase-likes` using that just-captured credential. Worker issues **one parameter-bound D1 DELETE** targeting the matching `visitor_hash`; trigger decrements affected counters. On confirmed D1 success the client may say only that current matching Like rows were deleted at that time.
- **No `like_erasure_blocks`, no extra migration, no suppression hashes, no 24-hour recovery proof in localStorage, no automatic retries, no silent backfill or cleanup.** Lost/weak legacy credentials cannot use the v2 self-service deletion endpoint; ordinary manual DSAR review remains necessary. On unavailable credentials, network failure, ambiguous response or database failure, say **"Löschung nicht bestätigt"** and direct the user to the privacy contact, without requesting raw IDs by ordinary email. Do not claim local ID removal or a server error proves live rows/backups/logs were deleted.

## Explicit remaining security trade-off

**Removing durable replay suppression is a conscious owner-approved source simplification.** The Worker does not expire v2 credentials server-side. An already-cached, copied or still-active credential — including one in another tab — **may re-create a Like after successful erasure**. A network race can do so too. The DELETE success means only *matching current rows were deleted*, not permanent non-reappearance or full GDPR erasure. No arbitrary 24h/12m deletion delay fixes replay while old tokens remain valid. Before Ready, security/legal review must assess whether this accepted residual risk is compatible with an effective Art. 17 erasure/right-to-withdrawal process; a later token revocation/expiry design needs its own owner authorization.

## v3 registry architecture — initial proposal, now Draft source implementation

**Status updated:** The originally proposed Worker-minted, 256-bit v3 bearer credential with hashed D1 purpose registration is now implemented as **Draft source**, not LIVE. The original one-statement v2 DELETE remains available exclusively as a deletion-only legacy route for securely held v2 tokens. The new v3 schema migration is present only as a file, without D1 deployment or controller-approved retention. The technical design is not a legal approval or a LIVE authorization.

### Minimal server contract

1. **Issuance only after explicit per-purpose choice:** Browser separately records Like/Print preferences first. A new same-origin, rate-limited Worker endpoint generates a fresh unguessable `v3-` token using `crypto.getRandomValues`; it never accepts a caller-supplied token to register or reactivate. Return the raw token **once** via HTTPS JSON with `Cache-Control: no-store`; persist only `SHA-256(token)` in D1. No token in URLs, cookies, logs, error messages or consent audit metadata. Validate request target/Origin/Fetch Metadata, body size and content type; fail closed when D1/rate limiting are unavailable.
2. **Single proposed D1 registry** (separate from the existing `likes` table): `visitor_credentials(visitor_hash PRIMARY KEY, like_allowed, print_allowed, notice_version, consent_recorded_at, expires_at)`. Store no raw identifier, IP, user-agent, child identity, parent details or individual print history. Record the server-observed consent event, notice version, scope and expiry for legal review; **do not** claim this alone proves a person (or parent) consented. The actual expiry and deletion schedule require controller/legal approval and must not be invented from provider defaults.
3. **Every personalized request is purpose-checked server-side:** `POST /page` (Like status) requires a valid active Like scope for personalized status; anonymous `GET /page` shows aggregate counts without any ID. `POST /like` and `POST /print` require an active, unexpired registration with the corresponding scope. Like **INSERT must be one guarded SQL write** conditioned on a still-active Like registration, not a prior JavaScript/SQL read followed by an unguarded INSERT; Like DELETE/unlike and status must obey the same authorization policy. Print aggregate increment must likewise be conditional on an active Print registration **within the D1 mutation**, not on a stale earlier check. Keep existing counters, and do not count rejected requests.
4. **Like withdrawal/erasure atomically disables re-insertion:** In **one D1 `batch()` transaction**, remove all `likes` rows matching the hash (existing delete trigger adjusts Like totals) and **remove or irrevocably downgrade Like authorization for that same hash**. If Print remains allowed, keep the existing credential Print-only, but never allow an old credential to re-enable its revoked Like scope. If both scopes end, delete the registration. After a committed transaction, stale tabs, in-flight Like writes and copied IDs must fail the guarded Like INSERT. A successful response refers only to current D1 matching rows and recorded scope; it does not promise backup/edge-log purge.
5. **Changes/renewals:** Adding a previously absent or withdrawn purpose requires **fresh explicit consent plus a newly minted token**, never reactivating the old hash. Retire the previous registration atomically; if Like remains consented across the rotation, preserve its Like rows/counters in the same transaction. A Print-only consent withdrawal keeps Like active without changing the identifier; a Like withdrawal with Print consent remaining downgrades the existing token to Print-only. Expired credentials cannot authorize an action or be re-registered; a fresh token needs a new valid consent event. On network ambiguity the browser stops the revoked purpose and reports **`Löschung nicht bestätigt`**, without falsely treating a failed response as confirmation. No automatic retry with a retained old proof.
6. **Lifecycle:** Enforce `expires_at` on every relevant request even before physical cleanup. Agree a proportionate maximum validity, Like-row/registration purge cadence and D1 backup/Time Travel retention before release; if automation is required it needs a separate reviewed Worker/Cloudflare authorization. Deleting registry rows never revalidates the old token because server issuance only mints *new* random IDs. No perpetual revocation tombstones, separate tracking DB, new secret or paid Cloudflare tier is intrinsically required.

### Legacy transition, tests and release gates

- **No replay window at acceptance:** When declaring the successor secure, reject all nonregistered or legacy v1/v2 IDs for `/like`, `/print` and personalized `/page`, across **every production hostname**; preserve anonymous aggregate `GET /page`. Do not expose an endpoint that re-registers a supplied v1/v2/v3 credential. Keep a narrowly scoped **legacy v2 deletion-only** route long enough for valid bearer holders to request deletion, without allowing legacy Likes to be written back. Legacy/weak/lost credentials need an honest GDPR Arts. 11/12/17 rights route; legacy orphan Likes and their retention require an independently approved decision. Close the legacy personalized GET query route separately. Old clients can temporarily lose personalized Likes during cutover; accept that explicitly rather than leaving replay-capable writes open.
- **Source acceptance tests:** new/refused/Like-only/Print-only/both, consent change + reload/two tabs, storage denial, random-token issuance, purpose enforcement in Worker (including forged old tokens), old Like → revoke → replay → no insert, concurrent revoke and Like mutation, D1 failure/ambiguous HTTP, expired credentials, re-consent yielding a different token, legacy delete-only, no ID in GET/logging, accurate aggregate counters, mobile/keyboard/accessibility. Verify delete-trigger counter behavior with real D1/SQLite transaction semantics and test conditional Print counter increments.
- **GDPR/TDDDG gate:** GDPR Arts. 6/7/8/13/17 and TDDDG §25 still require an actual owner/legal decision, not a green source test. Since the site targets ages 3–6, assess whether the online service is **offered directly to children**: where Art. 8 applies, Germany's threshold is 16 and consent/authorization from parental responsibility plus reasonable verification is required; do not treat an ordinary child's click as sufficient. Determine whether collection of this server-side consent record is necessary/proportionate, retention criteria, legitimate-interest basis for independent IP/day HMAC and security processing, Cloudflare processing roles/transfers/logging and operational DSAR workflow. Keep browsing, PNG download and A4 print usable without consent.
- **Deployment dependency:** A proposed D1 schema migration and Worker endpoint/policy change need **separate exact owner authorization** and read-only production preflight; PR #183 GitHub CI does not prove deployed state. Plan the potentially disruptive Worker-first legacy-write fence and frontend cutover so that existing cached JS cannot bypass it; the application and Worker are different deployment gates. Also reconcile the planned `Datenschutzerklärung` and legal pages in paired Draft PR #158 under its own source authorization. Do not claim Ready for either PR before the full review.
- **Alternatives rejected:** a pure client-side ID delete or one-shot D1 DELETE cannot prevent replay; an endless SHA-256 revocation blacklist avoids some replay but implies indefinite pseudonymous retention. A server-minted registration plus guarded writes provides permanent invalidation of the **old credential** without retaining a forever-blocked hash. It does **not** prevent an actor from making a new identity via a genuinely new registration; rate limiting/abuse controls remain independent.
