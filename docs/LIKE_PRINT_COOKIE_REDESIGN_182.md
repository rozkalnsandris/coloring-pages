## Product requirements and truth boundaries

- A returning visitor on the **same browser and same site host** should normally have their previous Like recognized a week later. No account, name, email, device fingerprint, permanent IP identifier or universal one-human-one-vote guarantee.
- **Like only:** after a voluntary, specific affirmative action, a random 256-bit, first-party, host-only browser cookie binds to a server-side D1 pseudonymous Like/session ledger. Never mint/read the Like cookie for Print, page visits or generic analytics. The server stores only its cryptographic digest, page IDs, minimal consent version/time and expiry; no raw bearer token or browser IP in D1 Like tables. D1's hash is **pseudonymous, not anonymous** while it allows recognition.
- Proposed cookie attributes: `__Secure-aw-like-v1`, `Secure; HttpOnly; SameSite=Lax; Path=/api/stats/like`; omit `Domain`; add `Max-Age` only after a proportionate retention period is approved. The `__Secure-` prefix and host-only/path scoping keep this cookie out of `/api/stats/print` requests. Different public domains create different cookies: do **not** silently treat visits across `ausmalwiese.de`, `www.ausmalwiese.de`, and `coloring.rozkalns.net` as the same visitor.
- **Print:** count explicit *print-intent actions* using `page_id` and allowlisted campaign (if any), increment aggregate `page_stats` and `daily_prints`/campaign counters. Do not accept/send `visitor_id`, cookie ID, IP-derived Like key or unique-print claim; do not store request IP in Print D1 tables. A browser/Cloudflare edge still processes normal HTTP request metadata, so `print is wholly anonymous end-to-end` is **not** established. The A4 print flow proceeds even when telemetry fails. Count attempts, not verified sheets.
- **No surprise site-wide consent:** Like may offer `Zustimmen` / `Ablehnen` before any persistent Like cookie. Refusal continues browsing/A4/download; separate persistent Print consent and v3 Print credentials are removed in the coordinated design. Do not assume a TDDDG §25 necessity exception or legal acceptance merely because the cookie serves a Like feature.
- Protect writes with exact target-Origin and same-origin checks, JSON-only POST, strict body shape/size, `Cache-Control: no-store`, a bounded pre-issuance rate limiter, and D1 unique constraints. Counter changes should use explicit **desired state** (like/unlike) and an atomic database guard, not a non-idempotent toggle that can reverse on a repeated network request. Avoid browser fingerprinting, IP-based persistent deduplication and unbounded per-IP D1 records.
- If browser cookies are blocked, never assert that Like was saved; show an accessible error while keeping aggregate counts/Print available. Rejections or network ambiguity must not display confirmed success. Only on confirmed revocation may the UI claim deletion of currently linked active D1 rows; D1 Time Travel/recovery and unrelated logs are outside that claim.

## Migration and count semantics — explicit release blockers

The existing Draft v3 flow uses `coloring-pages-visitor-v1` localStorage and `visitor_credentials`; the **LIVE** schema and already-stored `likes(page_id,visitor_hash)` must be verified separately. `cloudflare/stats-cookie-like-migration.sql` is a **source-only, unapplied** additive preparation for a new session ledger. It never modifies old likes, counters, v3 credentials, trigger definitions or any D1 LIVE database.

1. Make the old v1/v2/v3 credential **delete-only** after the reviewed cutover; do not reuse it as a new Like cookie, do not transfer its votes silently, do not silently delete or reinterpret existing Like totals. Verify applicability of the current v2 erasure path and any actual deployed v3 registry from fresh evidence before migration.
2. Provide user-directed, one-shot erasure of eligible legacy Likes with an exact secure proof and a clear confirmed/failed/unknown outcome. Never read/send weak or unrelated legacy IDs to a normal stats endpoint; an unknown deletion must not get an automatic retry. Lost credentials and backups require a documented data-subject-request procedure.
3. **Like-count policy is not yet approved.** Current D1 triggers decrement `page_stats.like_count` when `likes` rows are deleted. If the product requires lifetime aggregate counts to survive expiry, an independently reviewed, transactionally consistent **active-versus-archived** accounting migration is necessary before cleanup. Otherwise merely expiring a browser cookie either leaves pseudonymous Like rows indefinitely or causes public counts to fall. No unreviewed trigger rewrite, archival conversion, count reset or expired-row deletion.
4. A proposed **12-month** Like cookie/session duration is **not approved** and is not an automatic GDPR/TDDDG safe harbor. Choose a justified term, independent scheduled deletion/aggregation procedure, D1 recovery/Time Travel limitations (read-only Dashboard showed up-to-30-day restoration), and account for cookie deletion, expiry, cross-host browsers, and duplicates after retention. Do not claim one Like per person.
5. Keep the existing historical aggregate Print counts and visit/campaign data intact. Define controlled API cutover and cached-client behavior; older clients may still send v3 IDs until an explicit reviewed compatibility shutdown. Refuse new unauthorized legacy personalized writes after the cutover. No Worker, D1 migration, Cron, RPi5, DNS, merge or LIVE action here.

## Tests / implementation gates

- Browser: refusal reads/sets **no** Like cookie; consent sets it only in the Like endpoint; returning same-host browser sees prior Like, unlike removes one, and forbidden cookie/cross-origin/blocked storage fails closed.
- Worker: invalid/replayed/missing cookie, expired/revoked session, two racing like requests, repeated desired-state commands, unrelated origin, cross-host requests, expired token and rate-limit abuse cannot create a second vote or inflate counters.
- Print: count without `visitor_id` or Like cookie; invalid `page_id`, unauthenticated cross-origin writes and excessive traffic are rejected; printing always works even when counts fail. Remember Print is a *click/intention* metric.
- SQL: additive migration idempotent, respects exact digest constraints, leaves all existing `likes`, `page_stats` and triggers untouched; explicit future data/counter migration must have independent backups/verification and signed-off deletion semantics.
