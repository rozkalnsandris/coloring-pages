**Decided product intent (not implemented or published by this decision):**
- **180 days** is the intended fixed lifetime of the first-party Like cookie **and** its D1 pseudonymous session/Like association, measured from affirmative issuance. Do not silently extend that clock on page visits, Like clicks, Print, or renewal; require a new informed consent for a fresh session. This is an owner-approved **design duration, not an automatic legal safe harbor**. The need/proportionality and actual deletion criteria still require legal review under GDPR Article 5(1)(e), and `LIKE_COOKIE_TTL_SECONDS` has **not** been set in production by this decision.
- **Before expiry:** an explicit *unlike* removes the selected active Like; withdrawal of Like-cookie consent deletes **all active Like rows for that cookie** plus its D1 cookie session and expires the browser cookie. Corresponding displayed counts may decrease. A failed/ambiguous deletion must never be shown as successful or automatically retried. No change to A4 printing or page access.
- **At expiry:** convert only the expired session's **remaining active Likes** into **page-level genuinely anonymised lifetime aggregate counts** exactly once, then delete the session hash, per-page pseudonymous Like rows and any linkable consent/session metadata. Keep no per-cookie archive key, timestamp trail, hash mapping or fine-grained event rows that permit reidentification. Do not claim anonymous status without a documented singling-out/linkability/inference assessment; even a small page-level total must be assessed in its context.

Expiry does not by itself lower this combined count; active consent withdrawal **before** anonymisation does. After irreversible anonymisation, it is not possible to locate/remove that individual contribution: explain the timing and rights in advance. After expiry a fresh cookie may Like again, so this metric is **historical Like actions**, not unique people.
- **Existing legacy votes:** do **not** silently move, revoke, archive, rename, erase, double count or treat v1/v2/v3 Like hashes as new-cookie votes. The production deployment/schema must be attested from LIVE evidence first. Handle recoverable secure legacy erasure proofs and missing-proof/ambiguous DSAR cases in a separately reviewed process. Current legacy records have no confirmed universal 180-day retention rule.
- **Print:** count aggregate print *intents* only, with no stable Print browser credential. Processing of HTTP/IP metadata at edge/origin and separate daily visitor-HMAC statistics need independent assessment; do not market the whole site as anonymous.

## Product requirements and truth boundaries

- A returning visitor on the **same browser and same site host** should normally have their previous Like recognized a week later. No account, name, email, device fingerprint, permanent IP identifier or universal one-human-one-vote guarantee.
- **Like only:** after a voluntary, specific affirmative action, a random 256-bit, first-party, host-only browser cookie binds to a server-side D1 pseudonymous Like/session ledger. Never mint/read the Like cookie for Print, page visits or generic analytics. The server stores only its cryptographic digest, page IDs, minimal consent version/time and expiry; no raw bearer token or browser IP in D1 Like tables. D1's hash is **pseudonymous, not anonymous** while it allows recognition.
- Proposed cookie attributes: `__Secure-aw-like-v1`, `Secure; HttpOnly; SameSite=Lax; Path=/api/stats/like`; omit `Domain`; add `Max-Age` only after a proportionate retention period is approved. The `__Secure-` prefix and host-only/path scoping keep this cookie out of `/api/stats/print` requests. Different public domains create different cookies: do **not** silently treat visits across `ausmalwiese.de`, `www.ausmalwiese.de`, and `coloring.rozkalns.net` as the same visitor.
- **Print:** count explicit *print-intent actions* using `page_id` and allowlisted campaign (if any), increment aggregate `page_stats` and `daily_prints`/campaign counters. Do not accept/send `visitor_id`, cookie ID, IP-derived Like key or unique-print claim; do not store request IP in Print D1 tables. A browser/Cloudflare edge still processes normal HTTP request metadata, so `print is wholly anonymous end-to-end` is **not** established. The A4 print flow proceeds even when telemetry fails. Count attempts, not verified sheets.
- **No surprise site-wide consent:** Like may offer `Zustimmen` / `Ablehnen` before any persistent Like cookie. Refusal continues browsing/A4/download; separate persistent Print consent and v3 Print credentials are removed in the coordinated design. Do not assume a TDDDG §25 necessity exception or legal acceptance merely because the cookie serves a Like feature.
- Protect writes with exact target-Origin and same-origin checks, JSON-only POST, strict body shape/size, `Cache-Control: no-store`, a bounded pre-issuance rate limiter, and D1 unique constraints. Counter changes should use explicit **desired state** (like/unlike) and an atomic database guard, not a non-idempotent toggle that can reverse on a repeated network request. Avoid browser fingerprinting, IP-based persistent deduplication and unbounded per-IP D1 records.
- If browser cookies are blocked, never assert that Like was saved; show an accessible error while keeping aggregate counts/Print available. Rejections or network ambiguity must not display confirmed success. Only on confirmed revocation may the UI claim deletion of currently linked active D1 rows; D1 Time Travel/recovery and unrelated logs are outside that claim.

## Source implementation continuation (2026-10-15; no LIVE authority)

Source-only implementation uses the owner-selected **180-day lifetime from cookie issuance**, without sliding renewal. The new `archived_like_totals(page_id,like_count)` table contains only page-level aggregated counts. The existing `page_stats.like_count` remains the active + legacy vote counter maintained by unchanged insert/delete triggers. API readers combine the two totals; archival deletes expired cookie-linked rows and their session in one atomic `D1.batch`, preserving the combined count. A bounded selector operates on **at most 100 expired sessions per invocation**, and completed batches are idempotent.

A Worker `scheduled()` handler is defined in source, but **no Cron schedule has been configured**, no migration has been run and no D1 database has been changed. The migration must be applied before any separate Worker rollout, or reads against the archive table will fail; release sequencing, rollback/restore/backup implications, eventual cleanup cadence, D1 Free limits and sustained backlog must be independently reviewed. A pseudonym's per-page contributions are lost after successful archival: the historical aggregate is not a count of unique people.

**Withdrawal:** before expiry, the separate `forget` action removes all active browser-vote rows and its cookie session, reducing combined counts; individual `unlike` removes only the selected vote. The sum of expired anonymous votes is not user-erasable after genuine anonymisation. *Genuine anonymisation* still requires a case-specific singling-out/linkability assessment. No legacy tokens are auto-archived, merged or deleted: the legacy v2 proof/delete procedure, absent-proof DSAR and stale v3 endpoints remain independent review gates. The actual children's audience, legal basis, cookie notice and paired PR #158 German legal text also require sign-off; CI checks do not establish legal compliance.

## 2026-10-15 source follow-up: post-expiry erasure boundary, consent text and v3 DSAR semantics

**Expiry gap and proof limitations (DESIGN, release blocked):** A 180-day `Max-Age` browser cookie stops being sent by a conforming browser once it expires. `cookieLikeSession()` also refuses expired sessions. Consequently a former consenting browser **cannot** use the existing `/like/forget` action to select and delete linkable Likes which persist after cookie expiry but before the scheduled archive has completed. Merely removing the server-side expiry check would not solve this loss-of-proof condition and would weaken purpose/retention boundaries. No hidden extension of cookie TTL, secondary browser identifier, new persistent proof, magic recovery, fake erasure success or automatic retry is allowed by this source authorisation. The proper release plan must (a) disclose that withdrawal via settings works **while the cookie is valid**, (b) schedule and monitor timely, bounded archive + per-cookie deletion after expiry, including stale/backlogged Cron and restoration replays, (c) support separate, non-deceptive privacy contact/DSAR for an expired identifier when a lawful and technically sufficient proof is actually available, and (d) STOP rollout if the chosen retention/erasure policy cannot be made proportionate and verifiable. Until successful archival, these D1 rows remain pseudonymous; do not call them already anonymous merely because the browser cookie expired. The browser's existing `forget` action remains fail-closed on missing/expired session, and `180 days` alone is **not** a verified server deletion SLA.

**Legacy v3 DSAR result:** `/erase-legacy-v3` now distinguishes actual `likes_deleted` and `credential_revoked`, reporting `matched:true` only when at least one row matched, with unknown database mutation metadata returning an unconfirmed error. Deleting only an unused credential **does not** mean a Like was found or deleted. The UI must use a neutral confirmation when zero Likes were deleted; v2 deletion-only continues to require a positive match. A failed/ambiguous response is never automatically replayed. Invalid/lost v1/v2/v3 proofs and Time Travel recovery still require a separately reviewed manual DSAR process.

**Bounded concurrency validation:** offline SQLite multi-connection `BEGIN IMMEDIATE` interleaving tests exercise archive-vs-archive, archive-vs-user withdrawal and archive-vs-in-flight Like writes, preserve active-plus-archive totals, and show a successful archive cannot reintroduce a deleted session. They test SQLite serialisation, **not** real Cloudflare D1 request/Cron race performance or production evidence. D1's documented `batch()` transaction and prepared binding are prerequisites, not full release sign-off. Cloudflare [D1 transaction API](https://developers.cloudflare.com/d1/worker-api/d1-database/) / [Prepared statements](https://developers.cloudflare.com/d1/worker-api/prepared-statements/).
